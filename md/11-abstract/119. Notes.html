Section 11: Abstract Classes and Interfaces



Lecture 1: Abstraction


Introduction

Abstraction is one of the four fundamental pillars of Object-Oriented Programming. Its core principle is to hide complex implementation details while exposing only the essential, high-level functionalities. It allows us to manage complexity by creating a simplified model of a system. The goal is to separate what an object does from how it does it.

A perfect real-world analogy is driving a car. To make the car go faster, you press the accelerator pedal. You interact with a simple, abstract interface (the pedal). You don't need to know the complex mechanics happening under the hood—the fuel injection, the spark plugs firing, the pistons moving, the transmission shifting gears. All of that complexity is abstracted away, allowing you to use the car effectively without being an expert mechanic.


In C#, abstraction is not just a concept; it's a practical tool we use to design flexible and maintainable software. The two primary mechanisms for implementing abstraction are abstract classes and interfaces. They allow us to define "contracts" that other classes must follow, ensuring a level of consistency and predictability without dictating the specific implementation details.




Lecture 2: Abstract Classes


Introduction

An abstract class is a special type of base class that is incomplete and cannot be instantiated on its own. Its purpose is to serve as a common blueprint for a group of related derived classes. It acts as a hybrid, allowing you to provide some shared, concrete implementation (common methods and fields) while also defining a contract of abstract members that its derived classes are required to implement.


How It Works & Rules

  • Declaration: You declare a class as abstract using the abstract keyword: public abstract class Shape { ... }.

  • Instantiation: You cannot create an object of an abstract class. The line new Shape(); will result in a compiler error. It only exists to be inherited from.

  • Contents: An abstract class can contain everything a normal class can: fields, properties, constructors, and regular methods with full implementation.

  • Abstract Members: Its unique feature is that it can also contain abstract methods and properties, which we will cover in the next lecture.

  • Inheritance: Non-abstract child classes that inherit from an abstract class must provide an implementation for all of the inherited abstract members.


Why and When to Use It

Use an abstract class when you want to model an "is-a" relationship for a group of closely related classes that share common code. If you have several classes (Circle, Rectangle, Triangle) that are all types of Shape, and they all share a common property like Color or a common method like DisplayInfo(), an abstract class is the perfect choice. It allows you to write the common code once in the base class, avoiding duplication.


Example

C#

// This class cannot be instantiated directly. It's a conceptual blueprint.
public abstract class Shape
{
    // 1. Can have fields and properties with implementation.
    // This is common logic shared by all shapes.
    public string Color { get; set; }

    // 2. Can have a constructor, which is called by derived classes.
    public Shape(string color)
    {
        this.Color = color;
        Console.WriteLine("Shape constructor called.");
    }

    // 3. Can have regular, concrete methods.
    public void DisplayColor()
    {
        Console.WriteLine($"The color of this shape is {Color}.");
    }

    // 4. Can have abstract members (the contract).
    // This method has no body and must be implemented by derived classes.
    public abstract double CalculateArea(); 
}



Lecture 3: Abstract Methods


Introduction

An abstract method is a method that is declared inside an abstract class but has no implementation body. It consists only of a signature (access modifier, return type, name, and parameters) followed by a semicolon.


How It Works: The Contract

An abstract method establishes a mandatory contract. By declaring public abstract double CalculateArea();, the Shape abstract class is stating: "Any concrete class that wants to be considered a Shape must provide its own specific implementation of how to calculate its area. I, the Shape class, cannot provide a generic implementation because the formula is different for every shape."


Rules

  • An abstract method can only exist inside an abstract class.

  • It is declared with the abstract keyword and has no curly braces {} or method body.

  • Any non-abstract class that inherits from the abstract class must provide an implementation for all inherited abstract methods using the override keyword.


Example

Let's create concrete classes that inherit from Shape and fulfill its contract.

C#

public class Circle : Shape
{
    public double Radius { get; set; }

    // Call the base constructor to initialize the 'Color' property.
    public Circle(string color, double radius) : base(color)
    {
        this.Radius = radius;
    }

    // We MUST provide an implementation for the abstract method.
    // We use the 'override' keyword.
    public override double CalculateArea()
    {
        return Math.PI * Radius * Radius;
    }
}

public class Rectangle : Shape
{
    public double Width { get; set; }
    public double Height { get; set; }

    public Rectangle(string color, double width, double height) : base(color)
    {
        this.Width = width;
        this.Height = height;
    }

    // Provide the specific implementation for a rectangle's area.
    public override double CalculateArea()
    {
        return Width * Height;
    }
}

// --- In your Main method ---
Circle myCircle = new Circle("Red", 10);
Rectangle myRectangle = new Rectangle("Blue", 5, 10);

myCircle.DisplayColor(); // Calls the concrete method from the base Shape class.
Console.WriteLine($"Circle Area: {myCircle.CalculateArea()}"); // Calls the overridden method in the Circle class.

myRectangle.DisplayColor();
Console.WriteLine($"Rectangle Area: {myRectangle.CalculateArea()}");



Lecture 4: Interfaces


Introduction

An interface is a pure contract. It defines a set of related public members (methods, properties, events, or indexers) but provides no implementation for any of them. A class or struct that implements an interface makes a guarantee to the compiler that it will provide a public implementation for all members defined in that interface.

If an abstract class models an "is-a" relationship (a Circle is a Shape), an interface models a "can-do" capability (a Car, a Person, and a Document can all be ISerializable—they all have the capability of being saved).


How It Works & Rules

  • Declaration: You use the interface keyword. By convention, interface names start with a capital I, for example, ILogger or IDisposable.

  • Contents: Members inside an interface definition have no body and no access modifiers. They are all implicitly public.

  • Implementation: A class implements an interface using the colon (:) syntax, just like inheritance. The class must then provide a public implementation for every member defined in the interface.


When to Use It

Use an interface when you want to define a common capability that can be shared across unrelated classes. For example, you might have Car, Bird, and Drone classes. They have no logical "is-a" relationship, so they shouldn't share a common base class. However, they all have the ability to move, so they could all implement an IMovable interface.


Example

Let's define a contract for anything that can be saved.

C#

// The interface defines the "what" (the contract), not the "how".
public interface ISaveable
{
    void Save(); // No body, no access modifier.
}

// First class that implements the contract.
public class Document : ISaveable
{
    public string Text { get; set; }
    
    // It MUST provide a public implementation of the Save method.
    public void Save()
    {
        Console.WriteLine("Saving document to a .txt file...");
    }
}

// A completely unrelated class that also implements the contract.
public class PlayerProgress : ISaveable
{
    public int Level { get; set; }

    // It provides its own specific implementation of Save.
    public void Save()
    {
        Console.WriteLine("Saving player progress to the cloud...");
    }
}



Lecture 5: Dynamic Polymorphism using Interfaces


Introduction

One of the most powerful features of interfaces is their ability to enable polymorphism among completely unrelated classes. Polymorphism allows us to write code that can work with objects of different classes in a uniform way, as long as they all share a common interface. This means you can create more flexible, decoupled, and maintainable systems.


How It Works

You can create variables, method parameters, or collections (like a List) of an interface type (e.g., List<ISaveable>). These can hold a reference to an object of any class that implements that interface.

When you call a method through the interface reference (e.g., item.Save()), the .NET runtime performs a dynamic lookup. It checks the actual type of the object at that moment and executes the specific implementation of the method provided by that object's class.


When to Use It

Use this pattern whenever you need to perform a common action on a group of different objects. For example, you might want to save the state of various parts of your application (the user's progress, the document they are editing, the application settings) in one go. As long as each of these classes implements ISaveable, you can handle them all with the same code.


Example

Let's use the ISaveable interface and the Document and PlayerProgress classes from the previous lecture. We'll create a single method that can save any object that implements the contract.

C#

public interface ISaveable
{
    void Save();
}

public class Document : ISaveable
{
    public void Save()
    {
        Console.WriteLine("Saving document to a .txt file...");
    }
}

public class PlayerProgress : ISaveable
{
    public void Save()
    {
        Console.WriteLine("Saving player progress to the cloud...");
    }
}

public class ProgressManager
{
    // This method works with ANY object that implements ISaveable.
    // It is decoupled from the concrete Document and PlayerProgress classes.
    public void SaveAll(List<ISaveable> itemsToSave)
    {
        Console.WriteLine("\n--- Starting Save All Operation ---");
        foreach (ISaveable item in itemsToSave)
        {
            // At runtime, C# will call the correct Save() method
            // based on the actual object type of 'item'.
            item.Save();
        }
        Console.WriteLine("--- Save All Operation Complete ---");
    }
}

// --- In your Main method ---
Document myDoc = new Document();
PlayerProgress myProgress = new PlayerProgress();

// Create a list of the interface type.
List<ISaveable> saveableItems = new List<ISaveable>();

// We can add different types of objects to the same list.
saveableItems.Add(myDoc);
saveableItems.Add(myProgress);

ProgressManager manager = new ProgressManager();
manager.SaveAll(saveableItems);

Output:

--- Starting Save All Operation ---
Saving document to a .txt file...
Saving player progress to the cloud...
--- Save All Operation Complete ---



Lecture 6: Multiple Inheritance using Interfaces


Introduction

As we learned in the Inheritance section, C# enforces single inheritance for classes—a class can only inherit from one other base class. This rule prevents many complex problems. However, there are many situations where an object logically has multiple distinct roles or capabilities. Interfaces are the C# solution for achieving this form of multiple inheritance.


How It Works

A class can implement multiple interfaces. You simply list the interfaces after the colon, separated by commas. By doing so, the class promises to provide a public implementation for all members from all the interfaces it implements.

This allows a class to inherit a primary identity from its single base class (the "is-a" relationship) while also inheriting multiple sets of capabilities from various interfaces (the "can-do" relationships).


When to Use It

Use this pattern when you have a class that needs to conform to several different, unrelated contracts. A real-world example is an all-in-one printer/scanner/fax machine. It's one device, but it has multiple, distinct functionalities.


Example

Let's model a modern smartphone. It "is an" ElectronicDevice (its base identity), but it "can do" the job of a phone, a camera, and a GPS navigator.

C#

// --- The Contracts (Interfaces) ---
public interface IPhone
{
    void MakeCall(string number);
}

public interface ICamera
{
    void TakePhoto();
}

public interface IGps
{
    string GetCurrentLocation();
}

// --- The Base Class ---
public class ElectronicDevice
{
    public int BatteryLevel { get; protected set; } = 100;
}

// --- The Concrete Class Implementing Multiple Interfaces ---
// It inherits from ONE base class, but implements THREE interfaces.
public class SmartPhone : ElectronicDevice, IPhone, ICamera, IGps
{
    // Implementation for IPhone contract
    public void MakeCall(string number)
    {
        Console.WriteLine($"Calling {number}...");
        BatteryLevel -= 5;
    }

    // Implementation for ICamera contract
    public void TakePhoto()
    {
        Console.WriteLine("Taking a photo...");
        BatteryLevel -= 2;
    }

    // Implementation for IGps contract
    public string GetCurrentLocation()
    {
        Console.WriteLine("Finding current location...");
        BatteryLevel -= 3;
        return "Kuntloor, Telangana, India";
    }
}



Lecture 7: Interface Inheritance


Introduction

Just as classes can inherit from other classes, interfaces can also inherit from other interfaces. This allows you to build more complex contracts from smaller, more reusable ones, creating a logical hierarchy of capabilities.


How It Works

When a derived interface inherits from a base interface, it incorporates all the members of that base interface into its own contract. Consequently, any class that implements the derived interface must provide an implementation for all members from both the derived interface and all of its base interfaces.


When to Use It

Use interface inheritance to create layered or tiered API contracts. You can have a very basic interface and then create more specialized interfaces that add more functionality, allowing classes to choose the level of complexity they want to implement.


Example

Let's model a data access contract. Some data sources might be read-only, while others are read-write.

C#

// 1. The base contract: anything readable.
public interface IReadable
{
    string Read(int id);
}

// 2. A contract for anything writeable.
public interface IWriteable
{
    void Write(string data);
}

// 3. A derived interface that inherits from BOTH base interfaces.
// This creates a more complex contract for full read/write access.
public interface IReadWrite : IReadable, IWriteable
{
    // It can also add its own new members if needed.
    void Delete(int id);
}

// This class only needs to be readable.
public class ConfigurationReader : IReadable
{
    public string Read(int id) { /* ... logic ... */ return "config_value"; }
}

// This class needs the full read/write/delete functionality.
// By implementing IReadWrite, it MUST implement all three methods.
public class DatabaseConnection : IReadWrite
{
    public string Read(int id) { /* ... logic ... */ return "db_record"; }
    public void Write(string data) { /* ... logic ... */ }
    public void Delete(int id) { /* ... logic ... */ }
}



Lecture 8: Explicit Interface Implementation


Introduction

Explicit interface implementation is a technique where a class member that implements an interface member is not made public on the class itself. The member can only be accessed by first casting the object to the specific interface type.


How It Works: Syntax

To explicitly implement an interface member, you prefix the member name with the InterfaceName. and you do not use an access modifier (like public).

void IMyInterface.MyMethod() { ... }


Why and When to Use It

There are two primary reasons to use this technique:

  1. To Resolve Naming Collisions: This is the most common reason. It's used when a class implements two or more interfaces that happen to declare a member with the exact same name and signature. Explicit implementation allows the class to provide a separate implementation for each interface's member without conflict.

  2. To Hide Interface Members: Sometimes, an interface member is highly specialized or not part of the class's core public API. You can explicitly implement it to hide it from the class's main public surface, keeping the class's own API clean. The member is still accessible, but only to consumers who are specifically working with the interface.


Example: Resolving a Naming Collision

Imagine you have two interfaces for logging, both with a Log method, but they are expected to behave differently.

C#

public interface IFileLogger
{
    void Log(string message);
}

public interface IDatabaseLogger
{
    void Log(string message);
}

public class ReportGenerator : IFileLogger, IDatabaseLogger
{
    // Explicit implementation for IFileLogger.
    // Note: No 'public' access modifier.
    void IFileLogger.Log(string message)
    {
        Console.WriteLine($"Writing to file: {message}");
    }

    // Explicit implementation for IDatabaseLogger.
    void IDatabaseLogger.Log(string message)
    {
        Console.WriteLine($"Writing to database: {message}");
    }
}

// --- In your Main method ---
ReportGenerator report = new ReportGenerator();

// This would cause a compiler error because Log is not a public member of the class.
// report.Log("My message"); // ERROR!

// To call the methods, you must first cast the object to the specific interface.
IFileLogger fileLogger = report;
fileLogger.Log("File log entry."); // Output: Writing to file: File log entry.

IDatabaseLogger dbLogger = report;
dbLogger.Log("Database log entry."); // Output: Writing to database: Database log entry.



Lecture 9: IMP Points to Remember


Introduction

This lecture summarizes the most critical, practical, and interview-worthy points about abstract classes and interfaces. The ability to articulate their differences is a hallmark of a proficient C# developer.


Abstract Class vs. Interface: The Core Interview Question

This is one of the most common C# OOP interview questions. You must be able to compare them clearly.

  • Core Purpose:

    • Abstract Class: To provide a common base for a group of closely related classes. It models an "is-a" relationship (a Dog is an Animal).

    • Interface: To define a common capability or contract that can be implemented by unrelated classes. It models a "can-do" relationship (a Car and a Document can both be ISaveable).

  • Implementation:

    • Abstract Class: Can contain implementation details: fields, constructors, and methods with full bodies.

    • Interface: Is a pure contract and traditionally cannot contain implementation. (Note: Modern C# allows default interface methods, but for interview purposes, stick to the classic definition unless asked about new features).

  • Inheritance:

    • Abstract Class: A class can inherit from only one abstract class (single inheritance).

    • Interface: A class can implement multiple interfaces.

  • Members:

    • Abstract Class: Can have public, protected, private, etc. members. Can have static members and const fields.

    • Interface: All members are implicitly public. Cannot have instance fields or instance constructors.


abstract vs. virtual Methods

This is another common point of confusion.

  • An abstract method has no implementation and must be overridden by the first non-abstract derived class.

  • A virtual method has an implementation in the base class, and derived classes can optionally override it if they need to provide a more specific behavior.


Interfaces are Contracts for Decoupling

The primary power of interfaces is decoupling. When your code depends on an interface (ILogger) instead of a concrete class (FileLogger), you can easily swap out the implementation (e.g., change to a DatabaseLogger) without changing the code that uses it. This makes your applications more flexible, modular, and easier to test.
